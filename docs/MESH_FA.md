## دو کد مستقل، دقیقاً برای دو کار

| فایل | محل استقرار | تنظیمات لازم |
|---|---|---|
| [`manager-worker.js`](../manager-worker.js) | **یک Worker مرکزی جدید** | binding نوع D1 با نام **`DB`**، راز **`OWNER_KEY`**، یک راز مستقل **`NODE_KEY_<NAME>`** برای هر نود |
| [`node-worker.js`](../node-worker.js) | **هر یک از Workerهای نود** | متغیر **`NODE_ID`**، متغیر **`MANAGER_URL`** و راز **`NODE_KEY`** |

هر فایل، یک ES module **کامل و آمادهٔ paste** است. نصب Node/npm، build، VPS، نهان، KV، Durable Object یا افزونهٔ پولی برای اجرای کد لازم نیست. **نودها دیتابیس ندارند**؛ فقط مدیر مرکزی D1 دارد. رابط وب، فونت و QR محلی‌اند و از سایت دیگری دریافت نمی‌شوند.

فایل‌های همین شاخهٔ **`arena/4a2b629b-nexiup`** را بردارید؛ `main` عمداً دست‌نخورده است. **`worker.js`، نسخهٔ قدیمی/یکپارچهٔ ۲٫۱٫۲ با ربات است، نه فایل مدیریت Mesh.** `wrangler.toml` ریشه نیز مربوط به همان نسخهٔ قدیمی است؛ برای Mesh دو فایل پیکربندی مستقل وجود دارد.

**مرز مهاجرت:** حساب‌های Mesh در جدول‌های جدید `nx3_` و با API تازه هستند. ربات، پرداخت، کیف پول، معرفی، کاتالوگ ProxyIP و حساب‌های قبلی در `worker.js` حفظ شده‌اند، اما **ربات قدیمی خودکار حساب Mesh نمی‌فروشد/صادر نمی‌کند**. مهاجرت خودکار اطلاعات مالی، UUID، لینک و اشتراک قبلی انجام نشده است. Mesh را روی **Worker و origin جدید** راه‌اندازی کنید؛ جایگزین‌کردن endpoint فعالِ قدیمی، URLهای مشتریان قبلی را خودبه‌خود سازگار نمی‌کند. ابتدا از D1 پشتیبان بگیرید؛ دیتابیس جدا توصیه می‌شود. namespace جدا، سهمیهٔ Free جدید ایجاد نمی‌کند.

## امکانات پیاده‌سازی‌شده

- پنل مالک در `/` و `/admin`؛ فارسی/انگلیسی، RTL/LTR، دسکتاپ و موبایل.
- ورود واقعی با نشست هش‌شده در D1، کوکی `__Host-` امن/HttpOnly/Strict، مهلت ۳۰ دقیقه، کنترل دقیق Origin و CSRF، ابطال نشست هنگام خروج؛ بدون رمز پیش‌فرض یا ذخیرهٔ کلید در مرورگر.
- ثبت، ویرایش، تست، فعال/غیرفعال‌کردن حداکثر **۱۲ نود**؛ بدون نود/IP تولیدیِ ساختگیِ ازپیش‌فعال.
- تست API با **challenge یکتای مشاهده‌شده در خود مدیر**: مدیر ← نود ← مدیر. صرفاً JSON یا HTTP 200 با متن موفق کافی نیست. این تست، اثبات مسیر TCP، کشور خروجی یا اتصال اپراتور نیست.
- ساخت حساب با نام، یادداشت، مدت/انقضای دقیق، **حجم کل و روزانهٔ مثبت**، سقف پذیرش تونل هم‌زمان در کل شبکه، VLESS/Trojan/هر دو و انتخاب همه یا چند نود.
- حالت **همه** شامل نودهای فعال فعلی و آینده است؛ حالت **انتخابی** فقط موارد انتخاب‌شده. هویت حساب و سهمیه میان نودها و نسخه‌های اپراتوری مشترک است و یک URL اصلی تحویل می‌شود.
- ویرایش محدودیت بدون reset پنهان؛ تمدید از بزرگ‌ترِ «انقضای قبلی» و «اکنون»؛ توقف/ادامه/لغو؛ reset صریح مصرف؛ تعویض فقط لینک یا تعویض UUID. عملیات مدیریتی حساس، nonce ماندگار و کنترل نسخه دارند.
- تونل واقعی VLESS/Trojan روی TLS WebSocket برای **TCP**؛ اعمال سهمیه، برش آخرین قطعه به اندازهٔ باقیمانده، صف محدود، بستن صحیح سوکت و رفتار fail-closed هنگام شکست مجوز مرکزی. **UDP، Shadowsocks، XHTTP و gRPC در این جفت پیاده‌سازی نشده‌اند.**
- اشتراک raw/base64، JSON کامل Xray، QR واقعی PNG محلی و صفحهٔ کاربر. Clash/sing-box فقط تنظیمات قابل‌نمایش را می‌دهند؛ ضرورت‌های Xray بی‌صدا حذف نمی‌شوند.
- پروفایل مستقل و نسخه‌دار ایرانسل، همراه اول و استاندارد؛ دو ECH به شکل دو مقدار scalar/دو نسخهٔ جدا، با همان حساب؛ اعتبارسنجی و rollback. حفظ این تنظیمات به معنی تأیید اتصال امروزِ اپراتور یا هر نسخهٔ کلاینت نیست.
- Clean IP/host اختیاری و حداکثر چهار fallback از نوع `host:port` برای هر نود، از ورودی خود مدیر. query مشتری آن‌ها را عوض نمی‌کند. این آدرس‌ها **تست‌شده فرض نمی‌شوند**. پنل کامل کاتالوگ/تست کشوری قدیمی همچنان در Worker قدیمی است و به‌طور پنهان به Mesh وصل نشده است.
- نمایش جداگانهٔ مصرف گزارش‌شده، حجم رزروشده/نامشخص و تفکیک نود؛ رویدادهای مدیریتی؛ بررسی خواندنی دیپلوی؛ نگهداری محدود و اختیاری.

## نصب فقط با داشبورد Cloudflare

### ۱. Worker مرکزی

۱. اگر داده‌ای دارید، از D1 پشتیبان بگیرید. **Worker جدید** و دیتابیس D1 بسازید؛ **تمام `manager-worker.js`** را paste کنید، نه فایل‌های پوشهٔ توسعه‌ای `mesh/`.
۲. دیتابیس را با نام دقیق **`DB`** از نوع **D1 binding** متصل کنید. Variable متنی حاوی ID دیتابیس، binding نیست.
۳. Secret به نام **`OWNER_KEY`** با مقدار تصادفی ASCII به طول ۳۲ تا ۲۵۶ نویسه بسازید؛ آن را در password manager نگه دارید. در کد، Git، query آدرس، تلگرام یا تصویر منتشر نکنید. کلید نود با آن یکی نباشد.
۴. compatibility date را **`2026-10-20`** یا جدیدتر و flag را **`global_fetch_strictly_public`** قرار دهید؛ نسخهٔ فعال را Deploy کنید.
۵. `/health` باید **`component:"manager"`**، **`version:"3.0.0"`** و `database_checked:false` بدهد. این فقط زنده‌بودن handler است، نه آمادگی D1/شبکه.
۶. `/admin` را باز کنید و با `OWNER_KEY` وارد شوید. ورود اولِ احراز‌شده جدول‌ها را ایجاد می‌کند؛ بازکردن عمومی صفحه این کار را نمی‌کند. دکمهٔ «بررسی دیپلوی، بدون تغییر داده» پیش از مهاجرت هم کار می‌کند و جدول نمی‌سازد.
۷. در **تنظیمات**، **origin واقعی HTTPS مدیر مرکزی** را بدون مسیر/query ذخیره کنید. `MANAGER_URL` نود باید دقیقاً با آن یکی باشد. همهٔ لینک‌ها و QRها از این دامنه ساخته می‌شوند. تغییر دامنه، دامنهٔ قبلیِ ازکارافتاده را حفظ نمی‌کند.

### ۲. هر Worker نود

۱. یک Worker جدا بسازید و **تمام `node-worker.js`** را paste کنید. برای هر استقرار، نام Worker و NODE_ID متفاوت انتخاب کنید.
۲. Variable به نام **`NODE_ID`**: شناسهٔ انتخابی شما؛ حروف/عدد/زیرخط/خط تیره، حداکثر ۴۸ نویسه.
۳. Variable به نام **`MANAGER_URL`**: همان origin اصلی HTTPS مدیر که در تنظیمات پنل ذخیره کردید.
۴. Secret به نام **`NODE_KEY`**: مقدار تصادفی ASCII مستقل و ۳۲ تا ۲۵۶ نویسه‌ای، مخصوص **همین نود**؛ نه کلید مالک.
۵. همان compatibility date و `global_fetch_strictly_public` را تنظیم و Deploy کنید. **این نود D1، KV، cron، ROLE، MASTER_KEY یا نصب نهان نمی‌خواهد.**
۶. `/health` آن باید component برابر `node`، نسخهٔ ۳٫۰٫۰، `configured:true` و `database_required:false` داشته باشد. این پاسخ، آزمون TCP موفق ادعا نمی‌کند.

### ۳. ثبت و اتصال به مدیر

۱. در Worker **مرکزی**، Secret با نام مطابق `NODE_KEY_<NAME>` بسازید؛ **مقدارش دقیقاً همان NODE_KEY این نود** باشد. مقدار هر نود متفاوت باشد. D1 فقط نام مرجع را نگه می‌دارد، نه مقدار کلید.
۲. در پنل **نودهای شبکه**، NODE_ID دقیق، نام نمایشی، HTTPS origin واقعی نود و **نام مرجع Secret مرکزی** را ثبت کنید. مقدار کلید را در فرم نود ننویسید. کشور، ادعای اختیاری مدیر است؛ `ZZ` یعنی نامشخص، نه مدرک جغرافیای خروجی.
۳. ذخیره کنید. نود جدید غیرفعال است؛ **تست API** را اجرا و سپس **فعال‌سازی** کنید. تست موفق یعنی challenge واقعاً دوطرفه دیده شده است. تست ناموفق نود را غیرفعال می‌کند. تغییر origin یا مرجع کلید، تست تازه می‌خواهد.
۴. این روند را برای هر نود تکرار کنید. نود قدیمی نهان/Legacy با API متفاوت، نود Mesh محسوب نمی‌شود؛ فایل نود جدید را Deploy کنید، نه اینکه کلید master را جایگزین کنید.

### ۴. ساخت و تحویل اشتراک

۱. **اشتراک‌ها → ساخت اشتراک**؛ حجم کل و روزانه برحسب **GiB**، مدت، سقف تونل هم‌زمان، پروتکل و نودها را تعیین کنید. یک GiB برابر ۱٬۰۷۳٬۷۴۱٬۸۲۴ بایت است. سقف روزانه از کل بیشتر نباشد؛ صفر رد می‌شود، نه نامحدود.
۲. **همهٔ نودهای فعال فعلی و آینده** یا نودهای مشخص را انتخاب کنید. ساخت حساب، یک ثبت معتبر مرکزی است؛ رقابت نوشتن چند دیتابیس دوردست ندارد.
۳. ذخیره کنید؛ لینک اصلی، QR واقعی، دانلود کانفیگ‌ها و حسابداری نودها نمایش داده می‌شود. نود در اولین اتصال از مرکز مجوز می‌گیرد؛ **ساخت دستی حساب روی تک‌تک نودها لازم نیست**.
۴. برای حفظ Cipher Suites/Final Mask/ECH، **JSON کامل Xray** بهتر است. بعضی واردکننده‌های URI، `cs` را نادیده می‌گیرند و همهٔ کلاینت‌ها پروفایل پیشرفته را پشتیبانی نمی‌کنند. پیش از فروش، کلاینت/شبکهٔ واقعی را تست کنید.
۵. تمدید به‌طور پیش‌فرض UUID، لینک و مصرف را نگه می‌دارد. Reset انتخاب صریح است. **تعویض فقط لینک، UUID قبلاً دانلودشده را لغو نمی‌کند**؛ برای آن از تعویض UUID یا لغو اشتراک استفاده کنید.

## سهمیه واقعاً چطور بین نودها مشترک است؟

حساب ۱۰ GiB روی سه نود، **۱۰ GiB کل** دارد، نه ۳۰ GiB.

۱. هر تونل، هویت و عضویت نود مجاز را از مرکز بررسی می‌کند. پذیرش اتصال هم‌زمان در D1 مشترک سریال می‌شود، نه فقط داخل یک isolate. این **تعداد تونل** است، نه اثبات تعداد دستگاه؛ پایین‌آوردن سقف، پذیرش‌های تازه را محدود می‌کند و مجموعه‌ای از اتصال‌های قبلی را انتخابی اخراج نمی‌کند.
۲. شناسهٔ اتصال/اعتبار، تصادفی و خصوصی در خود نود ساخته می‌شود؛ مشتری آن را تعیین نمی‌کند. اعتبار اولیه حداکثر **۶۴ KiB** و اعتبار بعدی حداکثر **۴ MiB** است؛ همیشه با باقیماندهٔ کل و روزانه محدود می‌شود.
۳. triggerهای D1 در همان تراکنش، وضعیت فعلی حساب/نود و هر دو شمارنده را بررسی و **پیش از ارسال** حجم رزرو می‌کنند. درخواست هم‌زمان نودها نمی‌تواند مخزن مشترک را بیش‌ازحد تخصیص دهد. نبود جدول/trigger لازم، دسترسی را می‌بندد.
۴. رفت و برگشت از یک شمارندهٔ سریال استفاده می‌کنند و قطعهٔ آخر به اندازهٔ باقیمانده بریده می‌شود. معیار، payload **پذیرفته‌شده برای ارسال** است، نه سربار TLS/WS یا اثبات تحویل به برنامهٔ مقصد. نوشتن ناموفق ممکن است محافظه‌کارانه حساب شود.
۵. گزارش نهایی معتبر، اعتبار را فقط یک‌بار می‌بندد؛ رفت/برگشت صعودی ثبت و فقط حجم استفاده‌نشده بازگردانده می‌شود. گزارش تکراری، دوباره refund نمی‌کند. گزارش معمول در پایان اعتبار یا بسته‌شدن اتصال است، **نه هر فریم**؛ پنل شمارندهٔ لحظه‌ای تک‌تک بسته‌ها نیست.
۶. اگر نود ناپدید شود یا پاسخ تخصیص گم شود، حجم استفاده‌نشده **حدس زده و آزاد نمی‌شود**. اعتبار نامشخص در سهمیه باقی می‌ماند و جدا از مصرف گزارش‌شده دیده می‌شود. پاک‌سازی سوابق آن را آزاد یا مجموع‌ها را حذف نمی‌کند. مدیر بعد از بررسی می‌تواند سقف را صریحاً افزایش/reset کند؛ حجم نامشخص را «تحویل قطعی» ننامید.
۷. روز حسابداری **00:00 تا 24:00 UTC** است. اتصال در مرز روز و انقضای مطلقِ معلوم محدود می‌شود؛ اعتبار روز گذشته برای روز جدید قابل‌مصرف نیست. حجم کل هر روز reset نمی‌شود.
۸. مجوز حداکثر **۳۰ ثانیه** عمر دارد و هر **۲۰ ثانیه** بازبینی می‌شود. توقف/لغو، خاموش‌کردن نود، تغییر عضویت یا کوتاه‌کردن انقضا روی اتصال موجود تا این بازه اعمال می‌شود؛ اتصال جدید وضعیت فعلی را می‌بیند. قطع مدیر، اعتبار تازه را می‌بندد و با پایان مجوز یا زودتر در بازبینی ناموفق، تونل قطع می‌شود.
۹. Reset دورهٔ مصرف جدید می‌سازد و **۳۱٫۵ ثانیه مکث تخلیه** دارد؛ گزارش دیررس دورهٔ قبل از دورهٔ تازه کم نمی‌کند. تعویض UUID نسخهٔ مجوز جدا دارد، مصرف را حفظ و همان مکث را اعمال می‌کند. ساعت بستر تقریباً هم‌گام فرض می‌شود؛ نود از مهلت monotonic و کسر کل زمان رفت‌وبرگشت استفاده می‌کند، نه ساعت گوشی مشتری.
۱۰. هر تونل فعلاً حداکثر **چهار دقیقه** عمر، **۳۶ درخواست کنترل**، حداکثر پنج مقصد TCP ترتیبی، صف ورودی ۱ MiB و سقف پیام ۲۵۶ KiB دارد. کلاینت باید در این سقف‌ها دوباره وصل شود؛ انتقال بسیار طولانیِ بی‌وقفه تضمین نیست. پس از ارسال payload به مقصد، retry/failover کور انجام نمی‌شود.

**مرز اعتماد:** نودها باید تحت کنترل شما و با همین کد قابل‌بررسی باشند. نود مخربِ صاحب کلید می‌تواند دربارهٔ مصرف دروغ بگوید یا شمارندهٔ محلی را دور بزند؛ این طرح attestation سخت‌افزاری نیست. کلید نود، مجوز پنل مالک، فهرست حساب‌ها یا هویت نود دیگر نیست. UUID و URL/QR/کانفیگ، اعتبار دسترسی‌اند و باید خصوصی بمانند.

## API و امنیت عملیات

پنل مالک در `/api/…` است؛ خواندن با cookie و تغییر با Origin/CSRF، یا Bearer صریح مالک برای CLI مورد اعتماد. کنترل نودها **POST** احراز‌شدهٔ `/mesh/v1/ping`، `/open`، `/check`، `/grant` و `/close` است؛ کلید مستقل نود همراه `X-NexiUP-Node`. نود نمی‌تواند کوکی/کلید مالک را به‌جای کلید محدود خودش استفاده کند. نود، `GET /_mesh/health` محافظت‌شده و WebSocket در `/connect` دارد. قرارداد **`nexiup-mesh/1`** است، نه API نهان.

مسیرهای اصلی مالک: ورود/نشست/خروج، بررسی خواندنی، نمای کلی/تنظیمات، ثبت/تست نود، فهرست/ساخت/ویرایش/عملیات حساب، QR خصوصی مدیر، پروفایل/rollback، رویداد صفحه‌بندی‌شده و `POST /api/maintenance`. جزئیات مسیرها در [راهنمای انگلیسی](MESH.md#api-contract-and-authentication) و پیاده‌سازی اصلی هست.

ساخت حساب `nonce` تازهٔ ۳۲ تا ۶۴ رقم hex می‌خواهد؛ عملیات حساب نسخهٔ فعلی و nonce دارد. تکرار **همان درخواست با همان nonce**، اثر را تکرار نمی‌کند؛ تغییر بدنه با همان nonce رد می‌شود. اگر پاسخ تغییر گم شد، وضعیت را بررسی و همان شناسه را نگه دارید، نه اینکه تمدید/reset تازه‌ای بسازید. SQL پارامتری است. نوشتن سرور زیر timeout سراسری قرار نگرفته؛ RPC زمان‌دار نود ممکن است نتیجهٔ مبهم داشته باشد که پروتکل اعتبار آن را محافظه‌کارانه نگه می‌دارد.

## ظرفیت Free، نگهداری و پشتیبان

فقط مرکز، حساب/مجوز، نشست هش‌شده، نود/مرجع راز، مجموع کل/روز/نود، اتصال/اعتبار، نسخه پروفایل، receipt تکرارناپذیری و audit را نگه می‌دارد. جدول‌های قدیمی `nx_` تغییر نمی‌کنند. هیچ نوشتن D1 به‌ازای هر فریم یا KV ناسازگار برای ادعای سقف سراسری وجود ندارد.

ولی پذیرش اتصال، رزرو، گزارش نهایی و بازبینی ۲۰ثانیه‌ای، درخواست و نوشتن واقعی دارند؛ trigger و index هم هزینه دارند. **این کد تضمین سرویس پراکسی پرترافیکِ کاملاً رایگان نیست.** CPU/درخواست Workers، خواندن/نوشتن/index/فضای D1 و تعداد اتصال را روی حساب واقعی اندازه بگیرید. سهمیه همه Workerهای حساب مشترک است. guardِ ۴۶ دستور، benchmark ردیف صورتحساب نیست. محدودیت TCP و شرایط Cloudflare همچنان برقرارند؛ clean host/fallback خودکار آن‌ها را دور نمی‌زند.

cron اختیاری مرکز **`17 * * * *`** در هر اجرا حداکثر ۱۰۰ ردیف از هر جدول هدف را پاک می‌کند: نشست/probe منقضی، اعتبارهای قدیمی و اتصال قدیمیِ بدون ارجاع. اعتبار/اتصال حداقل هفت روز نگه داشته می‌شود؛ مجموع‌های حساب/روز/نود باقی می‌مانند. receipt عملیات، هویت و audit بی‌صدا پاک نمی‌شود. سقف پاک‌سازی ممکن است به سرویس شلوغ نرسد؛ فضای ذخیره و سیاست archive باید مدیریت شود. **نود cron لازم ندارد.**

برای پشتیبان کامل از **خروجی خصوصی D1 / Time Travel** و برای رازها از password manager استفاده کنید. دانلود لینک/QR، پشتیبان حسابداری نیست. بازیابی را روی مدیر غیرتولیدی جدا تست کنید. برای رفع 1101، D1 را حذف/reset نکنید.

## یافتهٔ واقعی دربارهٔ فایل پیوست و 1101

تفاوت سازگاری مشخص بازتولید شد: از تاریخ **2026-03-17**، پیام باینری WebSocket در Workers به‌طور پیش‌فرض **Blob** است، نه ArrayBuffer. فایل پیوست `binaryType='arraybuffer'` را صریح تنظیم کرده بود؛ NexiUP قدیمی ۲٫۱٫۱ این کار را نمی‌کرد. تست native قبل از اصلاح، **Blob و صفر بایت در تبدیل ساده** را دید و بعد از اصلاح، انتقال WS/TCP واقعی محلی کار کرد. **نود Mesh ۳٫۰٫۰ و Worker قدیمی ۲٫۱٫۲** هر دو قبل از `accept()` آن را تنظیم می‌کنند. fake تست‌ها هم اکنون پیش‌فرض جدید را مدل می‌کند.

این یافته **علت همهٔ 1101ها نیست** و علت خرابی نهانِ حساب شما هم ثابت نشده است: منبع نهان ۳٫۰٫۴ بررسی‌شده **از قبل binaryType را تنظیم کرده بود**. همچنین `request.fetcher` در types/runtime فعلی وجود دارد و import استاندارد سوکت هم در تست محلی کار کرد. شواهدی نداریم که کامنت اضافی تقریباً ۴٫۸ MB فایل پیوست، جلوی استثنا را بگیرد. هیچ padding، ادعای ضدتشخیص یا کد رابط/تونل بالادستیِ فاقد مجوز روشن کپی نشده است. منابع و hash در [RESEARCH.md](RESEARCH.md) هستند.

- `/health` نسخه/نوع Worker فعال را بدون D1 یا TCP نشان می‌دهد. برای آمادگی جدول/trigger از بررسی **خواندنی احراز‌شدهٔ مدیر** استفاده کنید.
- خطای معمول کد، نسخه و شناسهٔ تصادفی امن دارد. Variable متنی اختیاری **`NEXIUP_DIAGNOSTICS="true"`**، رویدادهای ثابت `nexiup_mesh_error` یا `nexiup_mesh_tunnel_error`، حتی پس از ارتقای WebSocket را بدون پیام خام، URL، کلید، بسته یا کانفیگ ثبت می‌کند. بعداً خاموش کنید.
- در **Workers & Pages → Worker → Logs → Live** همان رکوردها را ببینید. رویداد کامل بستر ممکن است URL/هدر حساس داشته باشد؛ **کل آن را منتشر نکنید**. خطای مهارشده ممکن است با وجود HTTP 5xx/بسته‌شدن تونل، outcome برابر `ok` داشته باشد.
- اگر خود `/health` هم صفحهٔ 1101 بستر است، فایل/نسخه/route فعال و exception بستر لازم است. خطای بارگذاری ماژول/بستر بیرون catch درخواست است. لاگ/دیپلوی حساب واقعی، اینترنت ایران و کلاینت واقعی در این محیط بررسی نشده؛ موفقیت workerd محلی، گواهی تولید نیست.

## تصمیم‌های طراحی و فرض‌های نیازمند تأیید

۱. دو خروجی مستقل، نه تغییر نقش یک فایل بزرگ یا fork رابط بی‌مجوز؛ مدیر import سوکت ندارد و نود API مستند سوکت را پس از مجوز می‌گیرد. boot عمومی هیچ‌کدام D1 نمی‌خواند.
۲. نود بدون state و دفتر معتبر مرکزی، نه سهمیه مستقل ضرب‌شونده یا شمارندهٔ KV eventually-consistent.
۳. رزرو/refund برای **عبور نکردن از سقف** بر حدس مصرف پس از crash مقدم است؛ مصرف گزارش‌شده و رزرو/نامشخص حتی در معنای header اشتراک روشن‌اند.
۴. مجوز زمان‌دار، نه وعدهٔ ابطال آنی جهانی؛ مکث reset/rotation، مرز UTC و سقف تونل سراسری صریح‌اند.
۵. نود تحت کنترل مدیر، راز مستقل قوی، Origin/CSRF، عدم دنبال‌کردن redirect دارای Authorization، بدون UI/کد بیرونی، مقدار IP/host/UUID تولیدی جعلی یا auto-deploy.
۶. ربات/حساب‌های قدیمی حفظ و جدا هستند؛ مهاجرت و اتصال مالی نیازمند طرح صریح است و خودکار/پنهان انجام نشده است.
۷. پیش از تولید، artifact فعال Cloudflare، TCP/کلاینت/اپراتور واقعی، پروفایل‌ها، ساعت، رفتار reconnect/رزرو، نگهداری ذخیره و ظرفیت واقعی Free بررسی شوند. از شبکهٔ ساختگی تست، موفقیت حساب/اینترنت واقعی نتیجه نمی‌شود.
